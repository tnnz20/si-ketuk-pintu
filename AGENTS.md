# Repository Guidelines

## Project Structure & Module Organization

This repository contains a Go API (Go 1.27+) and a React single-page application.

### Backend (`apps/backend/`)

- `cmd/` contains executable entry points: `web`, `migrate`, and seed tools.
- `internal/config/` wires the application; `internal/delivery/http/` defines routes, middleware, and handlers (`handler/`).
- `internal/usecase/` implements business rules; `internal/service/` houses domain services like file upload and validation; `internal/repository/` defines repository interface contracts with GORM implementations in `internal/repository/persistence/`; `entity/` and `model/` define database and API shapes.
- `db/migrations/` contains ordered SQL migrations; `test/integration/` tests the live database and HTTP behavior.

Keep dependencies flowing from handlers to use cases to services and repositories. Do not import `internal` packages across unrelated layers.

### Frontend (`apps/frontend/`)

- `src/layouts/` owns top-level layout shells: `main-layout.tsx` (public), `auth-layout.tsx` (authentication), and `dashboard-layout.tsx` (authenticated administration with responsive navigation).
- `src/pages/` owns route-level screens; `src/components/ui/` contains accessible headless UI primitives (Shadcn / Base UI with Tailwind CSS v4); `src/components/` contains reusable domain UI.
- `src/hooks/` houses domain custom hooks (`useRequests`, `useArchives`, `useDashboard`) and reactive session management (`useSession`, `SessionProvider`, route guards `RequireAuth`, `RedirectIfAuthenticated`).
- `src/lib/api/` is the backend client; `src/schemas/`, `src/types/`, and `src/constants/` hold validation, shared shapes, and values.
- `public/` holds static files; `dist/` is generated by the build and should not be edited.
- Universal path alias `@/*` maps to `./src/*`. Do not use fragmented legacy aliases (`@components`, `@lib`, `@app-types`).
- **UI Primitives Rule**: Do not create intermediate wrapper components in `src/components/shared/` for UI primitives (e.g. `Empty`, `Skeleton`, `Tooltip`, `Select`, `Table`, `Card`, `Input`, `Textarea`). Consumers must import directly from `@/components/ui/*`. Always prefer Shadcn UI primitives over raw HTML elements (`<input>`, `<select>`, `<textarea>`, `<label>`, `<table>`) for accessibility and visual consistency.
- **Date Picking Rule**: Use `DatePicker` (`@/components/ui/date-picker`) with `disablePastDates` for visit dates and reschedule dialogs. Past dates are automatically disabled and rendered with muted styling.

Root files: `.github/workflows/`, `compose.yaml`, `Makefile`, `apps/backend/api/API_CONTRACT.md`, and `docs/`.

## Build, Test, and Development Commands

Use `make` from the repository root:

- `make be-run` starts the API at `http://localhost:8080`; first copy `apps/backend/.env.example` to `apps/backend/.env`.
- `make fe-dev` starts the Vite development server; `make fe-build` type-checks and builds it.
- `make be-test-unit` runs Go unit tests. `make be-test` also starts PostgreSQL and runs integration tests.
- `make fe-lint` and `make fe-format-check` validate frontend code; `make fe-prettier` formats it. Run `npm run typecheck` in `apps/frontend/` for fast TypeScript-only checks.
- `make migrate-up` applies migrations; create one with `make migrate-create name=add_feature`.

Set `ENGINE=docker`.

## Coding Style & Naming Conventions

Format Go with `gofmt`; use idiomatic exported Go names and concise `CamelCase` types. Keep errors wrapped with operation context (`fmt.Errorf("open database: %w", err)`) so callers can use `errors.Is`.

Frontend code uses TypeScript, ESLint, Prettier, and Tailwind. Components use `PascalCase.tsx`; hooks and helpers use camelCase. Keep API payload names aligned with the backend contract, including snake_case JSON/form fields.

## Testing Guidelines

Add focused Go tests beside the package as `*_test.go`, named `Test<Behavior>`. Use `apps/backend/test/integration/` for database, migration, and HTTP behavior. Verify frontend changes with `npm run typecheck`, `npm run lint`, and a production build (`npm run build`).

## Commit & Pull Request Guidelines

Use conventional, imperative commit subjects such as `feat: add production turnstile protection`, `fix: normalize admin pagination`, or `docs: clarify bootstrap godoc`. Keep each commit scoped to one concern.

Pull requests should explain user-visible changes, configuration or migration steps, linked issues, and UI screenshots. State commands run before review.

## CI/CD & Deployment Workflows

GitHub Actions in `.github/workflows/` manage automated builds and deployments:

- `deploy-backend.yml` and `deploy-frontend.yml` build container images using Docker Buildx and BuildKit GHA caching (`scope=backend` vs `scope=frontend`).
- Image names are normalized to lowercase for GHCR (`ghcr.io/<repo>/<service>:<tag>`).
- Remote deployment connects over SSH using `SSH_KEY` and `SSH_PASSPHRASE` (avoiding password authentication).
- Remote service restarts use `podman compose -p si-ketuk-pintu up -d --no-deps <service>` to isolate application containers from PostgreSQL.

## Security & Configuration

Never commit `.env` files, credentials, JWT secrets, SSH private keys, or Turnstile keys. Update `.env.example` when adding required configuration, and keep production-only checks fail-closed. Deployment workflows authenticate using SSH key and passphrase only.
